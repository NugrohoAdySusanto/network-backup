Alur Enkripsi, Dekripsi & Perhitungan Matematis File Konfigurasi Jaringan di Ceph S3

Sistem menjamin kerahasiaan (confidentiality) dan keaslian/integritas (integrity) setiap file konfigurasi sebelum dikirim ke bucket Ceph S3. Data dimampatkan memakai zlib Deflate (NBZ1), disandikan langsung memakai Direct-DEK AES-256-GCM (AEAD) dengan header ringkas 16 byte (NBG2 ∥ Nonce) sebagai Additional Authenticated Data (AAD), serta disertai Tag GMAC 16 byte.

Rumus & Cara Perhitungan Enkripsi Konfigurasi ke Ceph S3

Disusun sebagai rumus terstruktur sesuai implementasi nyata pada kdf.py, vault_crypto.py, manifest_crypto.py, dan payload_crypto.py.

Standar: NIST SP 800-38D • RFC 8018 • RFC 1950

1. Hash Integritas & Deduplikasi (SHA-256)

Pre-Enkripsi
object_sha256  = Hex( SHA-256( raw_bytes ) )
content_sha256 = Hex( SHA-256( UTF8( normalize_config(raw_bytes) ) ) )
content_sha256 = Hex( SHA-256( UTF8( normalize_config(collected.text) ) ) )
  • • Keluaran SHA-256 = 256 bit = 32 byte = 64 karakter hex.
  • • object_sha256 = sidik jari biner asli untuk cek keutuhan saat restore.
  • • content_sha256 = kunci deduplikasi setelah baris dinamis dibersihkan driver.

2. Derivasi Kunci KEK (Vault NBV1 & Manifest NBM1)

100.000 Putaran
K_derived = PBKDF2-HMAC-SHA256(P, S, c = 100.000, dklen = 32B)
K_derived = U1 ⊕ U2 ⊕ … ⊕ U100.000
U1 = HMAC-SHA256(P, S ∥ INT_32_BE(1))
Ui = HMAC-SHA256(P, Ui-1),    2 ≤ i ≤ 100.000
N_hash = 2 × 100.000 = 200.000 operasi SHA-256
  • • P = APP_SECRET (Vault) / Master Password (Manifest); S = Salt acak 16 byte.
  • • AAD_32B = Magic (4B) ∥ Salt (16B) ∥ Nonce (12B) = 32 byte.
  • • Hasil DEK disimpan di self._cached_dek agar tidak diulang tiap file.

3. Resolusi Kunci Payload (Direct-DEK NBG2)

0 Putaran KDF
K_DEK = bytes(k),           jika k bertipe bytes & |k| = 32B
K_DEK = bytes.fromhex(k),   jika k string hex 64 karakter (standar DEK)
K_DEK = SHA-256(UTF8(k)),   jika k string/bytes lain (1x hash tunggal)
  • • DEK dari manifest dibuat lewat secrets.token_hex(32) (64 char hex = 256 bit).
  • • Ruang kunci = 2256 ≈ 1,158 × 1077 kombinasi kunci.

4. Kompresi Payload (NBZ1 + zlib DEFLATE L6)

RFC 1950/1951
M_comp  = b"NBZ1" ∥ DEFLATEL=6(raw_bytes)
|M_comp| = 4 + |DEFLATEL=6(raw_bytes)| byte
R_comp  = (|M_comp| / |raw_bytes|) × 100%
  • • NBZ1 = header penanda kompresi 4 byte (4e 42 5a 31).
  • • Stream zlib level 6 terdiri dari header 2B + blok DEFLATE + checksum Adler-32 4B.

5. Perhitungan Internal AES-256-GCM AEAD (Kerahasiaan & Autentikasi)

NIST SP 800-38D
5A. Inisialisasi & Enkripsi Stream (GCTR)
N  = CSPRNG(12B),   A = b"NBG2" ∥ N  (|A| = 16B = 128 bit)
J0 = N ∥ 0x00000001,    H = EK_DEK(0128)
n  = ⌈ |M_comp| / 16 ⌉ blok 128-bit (tanpa padding PKCS#7)
CBi = inc32i(J0),    i = 1, 2, …, n
Ci  = Pi ⊕ EK_DEK(CBi),    Cn* = Pn* ⊕ MSB|P_n*|(EK_DEK(CBn))
|C| = |M_comp|  (panjang ciphertext persis sama dengan input)
5B. Autentikasi Galois Field (GHASH & Tag GMAC)
u = 128 × ⌈ |C|bit / 128 ⌉ - |C|bit  (pad nol sementara di RAM)
X_input = A ∥ C ∥ 0u ∥ [|A|bit]64 ∥ [|C|bit]64
m = 1 (AAD) + n (Ciphertext) + 1 (Length Block) = n + 2 blok
Y0 = 0128,    Yi = (Yi-1 ⊕ Xi) • H  mod (x128+x7+x2+x+1)
T = MSB128( Ym ⊕ EK_DEK(J0) ),    |T| = 16 byte (128 bit)
  • • E_K(X) = enkripsi blok AES-256 (14 putaran).
  • • • H = perkalian polinomial pada Galois Field GF(2128).
  • • J_0 = counter awal khusus penutup tag GMAC (CB_1 mulai dari counter +1).
  • • Perubahan 1 bit di A, C, atau T membuat Y_m berubah total → InvalidTag.

6. Ukuran Akhir Amplop S3 (NBG2) & Syarat Validasi Restore (Fail-Closed)

Total Overhead = 36 Byte
Envelope_S3 = [NBG2 4B] ∥ [Nonce 12B] ∥ [C] ∥ [GMAC Tag 16B]
Overhead    = 4 (NBG2) + 12 (Nonce) + 4 (NBZ1) + 16 (Tag) = 36 byte
|Envelope_S3| = 36 + |DEFLATEL=6(raw_bytes)| byte
|Envelope_S3|min = 4 + 12 + 0 + 16 = 32 byte (batas cek header)
1) |Data| ≥ 32  ∧  Data[0:4] == b"NBG2"   (gagal → DecryptionError)
2) T_hitung == T_S3                    (gagal → IntegrityVerificationError)
3) M_dec = GCTR(inc32(J0), C_S3),   cek prefix b"NBZ1"
4) SHA-256(DEFLATE-1(M_dec[4:])) == object_sha256_DB

🛡️ Mengapa AEAD Satu Lintasan (AES-256-GCM)?

AES-256-GCM menggabungkan enkripsi stream (GCTR) dan autentikasi GMAC 128-bit (GHASH) dalam satu proses terakselerasi hardware sekaligus mengikat header 16-byte NBG2 ∥ Nonce. Tanpa padding blok, sistem kebal dari serangan Padding Oracle.

⚡ Mengapa Kompresi Sebelum Enkripsi?

Ciphertext berentropi tinggi bersifat acak mendekati sempurna sehingga tidak punya pola berulang untuk dikompresi. Mengompresi plaintext lebih dulu menghasilkan penghematan ruang storage Ceph S3 dan bandwidth transfer secara maksimal.

🔒 Mengapa Direct-DEK Tanpa PBKDF2 di Payload?

PBKDF2 (100.000 putaran) sudah melindungi rahasia manusia pada Database Vault (NBV1) dan Manifest KEK (NBM1). Karena DEK repositori sudah acak penuh 256-bit, pemakaian langsung menghilangkan antrean CPU tanpa mengurangi kekuatan kunci 2256.

Glosarium Istilah Kriptografi:

Plaintext
Teks konfigurasi asli sebelum disandikan yang masih terbaca sebagai teks UTF-8/ASCII.
Ciphertext
Deretan byte tersandi berentropi tinggi yang tidak bisa dibaca tanpa kunci DEK asli.
DEK 256-bit
Kunci acak 32 byte (Data Encryption Key) yang dibungkus di dalam repo_manifest.enc.
Nonce (12B)
Nilai acak 96-bit sekali pakai agar konfigurasi yang sama menghasilkan ciphertext berbeda.
Tag GMAC (16B)
Tag autentikasi 128-bit hasil perkalian Galois Field untuk membuktikan data & header tidak diubah.
AAD (16B)
Header terbuka (NBG2 ∥ Nonce) yang diikat matematis ke dalam perhitungan tag GMAC.
Ceph RGW S3
Penyimpanan objek terdistribusi yang kompatibel dengan protokol bucket AWS S3.
Fail-Closed
Prinsip keamanan: dekripsi langsung dibatalkan bila tag GMAC, kunci, atau header gagal validasi.
