Encryption & Decryption Pipeline for Network Device Configurations on Ceph S3 Storage

The system guarantees confidentiality and integrity of backup data prior to transmission to Ceph S3 buckets. Configurations are compressed with zlib Deflate, encrypted with authenticated AES-256-GCM (AEAD), and protected with Additional Authenticated Data (AAD) binding.

🛡️ Why Encrypt-then-MAC?

Computing HMAC over ciphertext (rather than plaintext) validates packet authenticity prior to decryption. If an attacker manipulates a single bit of ciphertext or IV, HMAC verification fails immediately and processing halts, preventing Padding Oracle Attacks.

⚡ Why Compress Before Encryption?

High-entropy ciphertext provides no repeating patterns for compression. Compressing before encryption yields maximum storage and transfer savings depending on device configuration text.

🔒 Key Derivation Parameters

The implementation derives 64 bytes of key material using PBKDF2-HMAC-SHA256 with 100,000 iterations and a random 16-byte salt, ensuring computational resistance against brute-force attacks.

Cryptographic Terminology Glossary:

Plaintext
Original unencrypted device configuration text, readable as plain UTF-8/ASCII.
Ciphertext
Encrypted high-entropy bytes unintelligible without the authentic symmetric key.
Salt
Random 16-byte nonce combined with master secret to defeat Rainbow Table attacks.
Initialization Vector (IV)
Random 16-byte block ensuring unique ciphertext across identical configuration uploads.
HMAC Tag
32-byte cryptographic message authentication code verifying data integrity in S3.
PKCS#7
Padding standard ensuring payload bytes align precisely with the 16-byte AES block size.
Ceph RGW S3
Distributed object storage platform providing AWS S3 API-compatible bucket storage.
Fail-Closed
Security policy where decryption immediately aborts if authentication tags do not match.
